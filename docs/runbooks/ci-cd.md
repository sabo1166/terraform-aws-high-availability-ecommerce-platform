# CI/CD runbook (GitHub Actions)

Status: workflows are written but **have never run**. They were checked locally only (YAML parsing and shell syntax). No GitHub remote is configured in this repository yet, and none of the configuration below exists.

## Workflows

| File | Trigger | Jobs |
| --- | --- | --- |
| `terraform.yml` | pull request; push to `main`/`master` (offline validation); manual (`workflow_dispatch`, deployment) | **offline-validate** (pull requests and pushes only): `terraform fmt -check -recursive`; `init -backend=false` + `validate` for `bootstrap/` and `environments/dev/`; both Python unit-test suites; no AWS, no backend, never deploys. Deployment (manual dispatch only) is **four separate jobs** chained with `needs`: **init** (1 INIT; no `needs`): fails fast, naming only what is missing, unless the repository-level variables `TF_STATE_BUCKET`, `TF_STATE_REGION`, `AWS_REGION` `DOMAIN_NAME`, `ROUTE53_HOSTED_ZONE_ID` and the repository-level secrets `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` are set (names only are reported, never values); sets up Terraform, configures the plan keys and initialises the S3 backend (a failure stops the run). **validate** (2 VALIDATE; `needs: init`): `terraform fmt -check -recursive`, then `init -backend=false` + `terraform validate`; no AWS credentials and no state. **plan** (3 PLAN; `needs: validate`): sets up Terraform, configures the plan keys and re-initialises the same S3 backend, then `terraform plan -out` (never `-destroy`; the provider region `aws_region` is passed from the same `AWS_REGION` variable that the credentials step uses); summary of addresses and actions only; **fails if the plan deletes or replaces any resource unless `allow_deletions` is selected**; the Lambda zip files written during the plan (`modules/automation/build/*.zip`) are checked (the alarm logger zip must exist and contain its handler) and packed into `lambda-builds.tar`; the plan, that tar and the metadata (commit SHA, plan SHA-256, tar SHA-256) are copied to the private state bucket under `ha-ecommerce/dev/plans/<run>-<attempt>/` with server-side encryption (read back and checked), never to a GitHub artifact; after a plan-only run (or when the apply stage will not run) the stored plan is deleted. **apply** (4 APPLY; `needs: plan`): runs only when the plan job succeeded, `apply` is true (the default) **and** the run is on the deployment branch; uses the `dev-apply` Environment, re-checks out the planned commit, downloads that exact plan and the Lambda tar from the state bucket, verifies the commit and both SHA-256 values, restores the zip files where the plan expects them, re-initialises the S3 backend and applies the saved plan with `terraform apply -auto-approve -input=false -lock-timeout=5m tfplan`; it never creates a plan, and deletes the stored plan only after a successful apply (a failed or cancelled apply keeps it for recovery until the lifecycle rule expires it). If init, validate or plan fails, is cancelled or is skipped, apply is skipped. |
| `application.yml` ("Application CI") | pull request / push touching `application/**`; manual | **frontend-ci**: Node from `.nvmrc`, `npm ci`, `npm test`, `npm run build`, verifies `dist/index.html` and `dist/assets`, uploads `frontend-dist-<sha>-<attempt>` (fails if the output is missing). **backend-ci**: `mysql:8.0` service container, Node from `.nvmrc`, `npm ci`, `npm run typecheck`, `npm test` once with a JSON report, then a guard step that **fails unless the MySQL contract tests are present in the report, all passed, nothing was skipped, and no suite failed** (so they cannot be silently skipped, removed, or hidden behind a failed `beforeAll`), `npm run build`, verifies `dist/server.js`, `dist/db/migrate.js` and the SQL migration, uploads `backend-dist-<sha>-<attempt>`. **infrastructure-check** (optional; runs only on manual dispatch with `check_infrastructure` selected, after both CI jobs): reports which secrets or variables are missing (names only), checks that AWS accepts the credentials, initialises the S3 backend and reads `frontend_asg_name` / `backend_asg_name`, and confirms both Auto Scaling Groups have only in-service, ELB-healthy instances; read-only. **ci-summary** ("CI Summary", always runs): writes a results table to the run summary and fails if frontend-ci or backend-ci did not succeed, or if the infrastructure check failed or was cancelled; a skipped optional check does not fail CI. There is **no deploy job**: the Terraform resources define no deployment mechanism (`docs/runbooks/application-deployment.md`). |

Terraform apply is never triggered by a push or by the application workflow, and no workflow runs destroy.

## Prerequisites that do not exist yet

GitHub **repository-level variables** (the init and plan jobs have no Environment, so Environment-level variables are not visible to them): `AWS_REGION`, `TF_STATE_BUCKET`, `TF_STATE_REGION`, `DOMAIN_NAME`, `ROUTE53_HOSTED_ZONE_ID`. `ALB_LOGS_BUCKET_NAME` is **no longer used** (the workflow does not pass it): the ALB log bucket is named `<project>-<environment>-alb-logs-<account id>-<region>`, which is unique per account and region. If you still have that repository variable you can delete it; a value copied from someone else's bucket name would collide.

**Secrets** (repository level): `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` for the **plan** identity. The same two names are also stored as **secrets of the `dev-apply` Environment** for the **apply** identity; inside the apply job the Environment values override the repository ones. No other secret is required: `TFPLAN_ENCRYPTION_KEY` is no longer used (saved plans are stored in the private state bucket, not as encrypted GitHub artifacts), and `ORIGIN_VERIFY_HEADER_VALUE` is no longer used (Terraform generates the CloudFront-to-ALB origin secret with `random_password`; to pin your own value set `TF_VAR_origin_verify_header_value` for local runs).

**GitHub Environments**: `dev-apply`, with its own `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` secrets (the apply identity), a deployment-branch restriction, and **no required reviewers and no wait timer** if you want the apply to run automatically (see "Enabling automatic apply" below). (A deployment Environment will be needed when an application deploy job exists.)

**AWS**: two IAM users, created by you outside this repository, each with its own access key pair: a **plan** user and an **apply** user. Both need the state-bucket access policy (`state_access_policy_json`, see `bootstrap/README.md`). The plan user additionally needs whatever read permissions Terraform's refresh requires; the apply user needs permission to create and change the resources in this stack (deliberately not `AdministratorAccess`). Those two permission sets are **not defined anywhere in this repository** and need their own design and review. The application infrastructure check in `application.yml` reuses the repository-level (plan) keys and only needs state read plus `autoscaling:DescribeAutoScalingGroups`.

**State**: the bootstrap stack applied and the S3 bucket available (`bootstrap/README.md`). The deploy workflow copies `backend.tf.example` to `backend.tf` at run time and passes the bucket and region with `-backend-config`; no backend file is committed.

**Application**: `application.yml` uses the Node.js version in each app's `.nvmrc` (22), `npm ci` with the committed `package-lock.json`, and the `test`, `typecheck`, and `build` scripts. The backend job's MySQL service uses an empty root password on a throwaway container that exists only for that job. This workflow has not run on GitHub: the MySQL contract tests in particular have never executed anywhere.

## Safeguards in the Terraform deployment jobs

- Manual dispatch only; `apply` defaults to **true** and `allow_deletions` defaults to **false**; one deployment run at a time (concurrency group `terraform-deploy`, no cancellation), in addition to the S3 lock file.
- The apply job only runs on the deployment branch: the repository variable `TF_DEPLOY_BRANCH` (default `master` if unset). A dispatch from any other branch can still plan but never applies.
- Deletion and replacement protection: the plan stage fails if any resource change includes a delete action (replacements contain one); because the apply job only applies the saved plan, nothing destructive can be applied unless a human re-ran the workflow with `allow_deletions` selected. `terraform destroy` is never run.
- The plan is written with `-out`, its stdout is discarded, and only resource addresses and actions go to the job summary. The saved plan can contain secrets, so it is never uploaded as a GitHub artifact (artifacts of a public repository are readable by anyone). It is copied to the private state bucket with SSE-S3 requested on each object, the stored encryption is read back and the run fails if it is not `AES256`, and plaintext plan files are removed from the runner. Access to the stored plan is the same as access to the state: the IAM policy that covers `ha-ecommerce/dev/*`.
- The apply job checks out the exact commit recorded by the plan job (not the branch tip), verifies `git rev-parse HEAD`, verifies the commit and plan SHA-256 recorded in the stored `plan-meta.txt` and the SHA-256 of the downloaded file against the plan job outputs (GitHub-held, not stored in S3), and applies the **saved plan**, so only the reviewed changes are applied. Terraform rejects a saved plan when the state changed since it was created.
- Authentication uses static access keys (no OIDC; no `id-token` permission). The workflows read them only from `secrets.AWS_ACCESS_KEY_ID` and `secrets.AWS_SECRET_ACCESS_KEY`, never echo them, and never write them to files; GitHub masks secret values in logs.
- Access boundary (intended): the init and plan jobs have no Environment and use the repository-level keys; the apply job runs in `dev-apply` and is meant to use that Environment's keys. The `validate` job, the `offline-validate` job and pull requests use no AWS credentials. The workflow only references `secrets.AWS_ACCESS_KEY_ID` / `secrets.AWS_SECRET_ACCESS_KEY` in each job; it does **not** verify that the Environment holds different keys (see the limitations below).
- Fresh runners: every job starts on a clean runner, so nothing under `.terraform` is carried between jobs. The init, plan and apply jobs each set up Terraform and initialise the same S3 backend (`backend.tf.example` copied to `backend.tf` at run time, bucket and region from the variables); the validate job uses `-backend=false`. Between jobs only the plan job's non-secret outputs (artifact name, commit SHA, plan SHA-256) and the encrypted plan artifact are passed. The init, validate and plan jobs check out `github.sha`; the apply job checks out the commit recorded by the plan job.

### Saved-plan storage in the state bucket

- Location: `s3://<TF_STATE_BUCKET>/ha-ecommerce/dev/plans/<run_id>-<run_attempt>/` with `tfplan` and `plan-meta.txt`. The prefix is `PLAN_KEY_PREFIX` in the workflow and sits under the state prefix, so the existing state access policy (`ListBucket`, `GetObject`, `PutObject`, `DeleteObject` on `ha-ecommerce/dev/*`) covers it with no IAM change. Anyone who can read the state can read a stored plan; plans carry the same sensitivity as state.
- Protection relies on the bucket created by `bootstrap/`: Block Public Access, `BucketOwnerEnforced`, versioning, default SSE-S3, TLS-only policy. The workflow also requests SSE-S3 per object and fails if the stored object does not report `AES256`. The workflow **cannot** check Block Public Access or the bucket policy (the CI policy has no `s3:Get*Bucket*` permissions): verify them once as described in `bootstrap/README.md`.
- Cleanup: the apply job deletes the stored plan only after a successful apply; the plan job deletes it for plan-only runs and runs where apply will not run. A failed or cancelled apply keeps the plan so **Re-run failed jobs** can use it. Because the bucket is versioned, a deletion leaves a noncurrent version. The `expire-saved-plans` lifecycle rule in `bootstrap/` (current objects after 7 days, noncurrent versions after 1 day, only under `<state prefix>plans/`) removes leftovers. **That rule exists only after the bootstrap stack is re-applied by an administrator**; until then leftovers expire under the general noncurrent-version rule (90 days by default).
- Integrity: the stored `tfplan` is trusted only if its SHA-256 and the recorded commit match the plan job's outputs, which GitHub holds outside S3. Someone with write access to the bucket prefix can replace the object, but the apply job then refuses it.

### Lambda packages and the saved plan

The `archive_file` data sources in `modules/automation` write `modules/automation/build/alarm_logger.zip` (and `health_monitor.zip` when the health monitor is enabled) **while `terraform plan` runs**. Terraform does not read data sources again when it applies a saved plan, and the apply job runs on a fresh runner, so without help the files would not exist there and the Lambda resources would fail with `open modules/automation/build/alarm_logger.zip: no such file or directory`. The plan job therefore verifies the zips, stores them as `lambda-builds.tar` next to the plan, and the apply job restores them after checking the tar's SHA-256. Shipping the same bytes (instead of rebuilding them) keeps the `source_code_hash` in the plan valid. The tar can only contain `modules/automation/build/` and `.zip` files directly in it.

### Security limitations of access keys

- Static keys are long-lived and are not scoped to a repository, branch, or workflow: anyone with the key pair can use it from anywhere until it is deactivated. OIDC roles avoid this; they were replaced here by your decision for this lab. Rotate or delete the keys when the lab ends.
- The repository-level (plan) keys are readable by any workflow run in this repository, including runs of a branch edited by someone with write access. Keep the plan user's permissions limited to state access and reads, and consider putting those keys in a branch-restricted Environment instead (not configured here).
- If the `dev-apply` Environment has no secrets of its own, GitHub silently falls back to the repository keys for the apply job, which removes the separation. The workflow cannot detect this (the INIT precheck only confirms the repository-level plan keys exist, and the apply job cannot tell which level a secret came from), so verify manually that `dev-apply` holds its own key pair, for example by checking that the access key ID shown in the AWS console for each IAM user differs.
- Required reviewers on `dev-apply` gate the apply keys; they do not limit what an approved (or automatic) apply can do.
- With `apply` true and no reviewers, **anyone who can run workflows in the repository (write access) can trigger an apply** on the deployment branch. Protect that branch (pull-request reviews, restricted pushes) and keep write access small.

## Known limitations

- Never executed: expect first-run fixes. Action versions use major tags (Node 24 majors: `checkout@v7`, `setup-node@v7`, `setup-python@v7`, `upload-artifact@v7`, `download-artifact@v8`, `setup-terraform@v4`, `configure-aws-credentials@v6`), not commit SHAs; pin SHAs after verifying them. Jobs run on the pinned `ubuntu-24.04` image instead of `ubuntu-latest`, so GitHub's gradual `-latest` migration cannot change the OS under a pipeline; move the pin deliberately (for example to `ubuntu-26.04`) after a validation run.
- Lock files hold hashes from the machine that created them; `terraform init` on Linux runners may fail or want updates if a platform hash is missing. If that happens, run `terraform providers lock` for `linux_amd64` and commit the result. `-lockfile=readonly` is not used for this reason.
- Reviewers see only addresses and actions, not attribute-level diffs, to avoid exposing sensitive values; a deeper review needs a separate, access-controlled process.
- `terraform_version: "^1.10.0"` accepts any 1.x release from 1.10; pin an exact version for fully reproducible runs.

## Enabling automatic apply (manual GitHub configuration)

The workflow cannot remove approval gates by itself: those are GitHub settings. For a dispatch to plan and then apply with no human step:

1. **Environment `dev-apply`** (Settings, Environments): delete every **required reviewer** rule and set the **wait timer** to 0. If either remains, the apply job stops at "Waiting for review".
2. In the same Environment, set **Deployment branches** to the deployment branch only, and add the apply identity's `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` as **Environment secrets**.
3. **Repository secrets:** `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` (plan identity); nothing else.
4. **Repository variables:** `AWS_REGION`, `TF_STATE_BUCKET`, `TF_STATE_REGION`, `DOMAIN_NAME`, `ROUTE53_HOSTED_ZONE_ID`, and optionally `TF_DEPLOY_BRANCH` (default `master`; set it if your deployment branch is not `master`).
5. **Branch protection** on the deployment branch (strongly recommended, since no approval remains): require pull requests and reviews, restrict who can push, and keep the offline `Terraform` validation check required.
6. **Prerequisites outside GitHub:** the state bucket from `bootstrap/`, the two IAM users (plan and apply) with the permissions you designed, and a real domain and hosted zone.
7. Run the workflow from the deployment branch: **Actions, Terraform, Run workflow**, leaving `apply` checked and `allow_deletions` unchecked.

Not done here: this task did not change GitHub settings, create the Environment or any secret, contact AWS or GitHub, or run `terraform apply`. Pushes still never trigger a deployment; only a manual dispatch does.
